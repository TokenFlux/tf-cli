## 记下来的教训

**判据要挑不会变的那个。** 分组准入放文案比放状态码稳（状态码见过 403 /
404 / 503 三种）；额度放 `remaining` 比放 `status` 字符串稳
（`status` 的取值集合没有文档）。两次结论方向相反，因为稳的东西不同。

**「诚实地不作为」不是安全选项。** 补全返回空、不发 `\r`、不复位终端 ——
在真实环境里都会被解释成别的东西。没得说时也得说点什么。

**同一份信息只该有一处。** 补全的命令名单是手写的第二份，加了 `tf status`
之后它不知道，而两份长得一样，看代码时不会觉得有问题。

**服务端的字符串没有语言。** 把网关返回的「推理积分」嵌进句子模板，
中文碰巧通顺，英文成了 `0/10 推理积分 left`。数据只能当数据摆着。

**测试锁的必须是事实。** 曾写测试断言「anthropic base 不带 `/v1`」，
把一个错误固化了；今天又有一条测试锁着刚被判定为设计缺陷的 `-y` 行为。

**结论要由命令自己说。** 我一直用 `grep -E "^(FAIL|---)"` 筛 `make check`
的输出，而 `go vet` 的错误两个都不匹配 —— 一次编译不过的测试因此一路
过了本地、进了提交、红在 CI 上。
